# ops-backup 设计文档

## 目标

- 为 SQLite、MySQL、PostgreSQL 与七牛 Kodo 提供可校验的备份和恢复入口。
- 恢复前发现损坏文件、路径穿越和远端对象冲突，避免数据库指向缺失媒体。
- 凭据、DSN、签名 URL、对象键和外部命令错误不进入日志或 manifest。

## 数据格式

每次备份创建独立目录，其中 `manifest.json` 记录格式版本、应用版本、数据库驱动及每个文件的大小和 SHA-256。Kodo 对象的原始键只存放在 manifest 中，本地文件路径由对象键的 SHA-256 推导，不能由输入直接拼接。

数据库和对象存储无法形成跨系统原子快照，因此一致性备份要求先停止应用与 Worker。备份按“对象、数据库、manifest”执行；恢复先校验全部文件和 Kodo 冲突，再恢复对象，最后恢复数据库。

## 方案选择与权衡

- 数据库采用 SQLite 原生快照和 MySQL/PostgreSQL 官方客户端，不在 Go 内重复实现数据库导出协议；代价是运行镜像需要额外安装两个客户端。
- Kodo 沿用项目现有、仍受维护的 `storage` API，减少同时引入 `storagev2` 的抽象；后续项目整体迁移 SDK 时再统一调整。
- 备份对象使用 SHA-256 文件名而不是保留原目录层级，牺牲人工浏览便利性，换取跨平台路径稳定性和明确的路径穿越边界。
- 不尝试删除目标空间中的额外对象，也不自动覆盖冲突对象，优先保证恢复操作可预测。

## 数据库策略

- SQLite 使用 `VACUUM INTO` 创建在线一致性快照。恢复前执行 `PRAGMA quick_check`，替换前将原数据库、WAL 和 SHM 文件改名保留。
- MySQL 使用 `mysqldump` 与 `mysql`，密码仅通过 `MYSQL_PWD` 传递。
- PostgreSQL 使用 custom-format `pg_dump` 与 `pg_restore`，DSN 仅通过 `PGDATABASE` 传递。

## Kodo 策略

备份分页列举所有对象，通过短期私有 URL 下载，限制读取长度并同时校验远端大小和本地 SHA-256。禁用状态对象会使备份失败，因为当前恢复格式无法无损表达该状态。

恢复默认跳过 ETag 和大小一致的对象；同名但内容不同的对象默认拒绝，只有显式传入 `--overwrite-objects` 才覆盖。恢复不会删除目标空间内备份之外的对象。

## 安全边界

- `restore` 必须提供精确确认词 `RESTORE`。
- 所有相对路径必须位于备份根目录且不能经过符号链接。
- 恢复前完整验证数据库和对象文件的大小、SHA-256、唯一键及唯一文件名。
- JSON 日志只记录阶段、数量、字节数和备份目录；错误只记录 Go 错误类型。

## 已知限制

- 一致性依赖运维人员在备份和恢复期间停止 `app` 与 `batch-worker`。
- MySQL 和 PostgreSQL 需要运行镜像中的官方客户端与服务端版本兼容。
- 备份目录未内置加密和异机复制，生产环境必须由外部备份系统完成加密、保留和异地存储。

## 变更历史

### 初始版本

新增三种数据库与 Kodo 的完整备份恢复流程、版本化 manifest、恢复确认、完整性校验和容器运维入口，用于补齐上线前数据灾备能力。
