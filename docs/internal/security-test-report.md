# 安全测试历史记录（内部）

> 原报告提供的请求次数和线上结果未在本轮重跑，缺少原始请求/响应附件的条目仅保留为待核验记录。代码已按下述问题加固，当前实现与验收步骤见 [security-hardening.md](./security-hardening.md)。本文描述修复前状态，不能用于判断当前线上版本是否安全。

## 结论

原报告所列用例未报告成功获取后台权限。以下项目混合了黑盒观察与源码检查，不能推出已覆盖所有提权通道：

纵向越权、横向企业越权、JWT 伪造与 claims 篡改、路径穿越、SSRF、存储型 XSS、SQL 注入、跨用户缓存泄漏。

本次记录的主要风险包括「凭据入口本身缺乏防护」：后台登录没有速率限制、没有失败锁定、没有二次验证；会话不可吊销；失败流量在审计日志中无法溯源。也就是说，**未观察到应用层登录限流，且没有独立的认证失败审计事件**，这是原报告列出的主要安全欠账。

## 二、缺陷清单

### H-1 后台登录无速率限制、无失败锁定、无二次验证

**现象**：连续 188 次失败登录（约 3 分钟，4 个用户名 × 47 个高危弱口令），全部返回 `200 + code:1`，无一次 429、无账号锁定、无验证码。

**影响**：管理员弱口令或复用口令会增加在线猜测风险，无法根据当前样本推算攻破时间；还需验证边缘 WAF 与运维告警配置。

**修复**：两个登录端点共享 IP 与规范化账号限流，计入并发在途请求；后台人机验证必须在服务端完成，普通登录不能绕过。原示例只有读取计数而没有写入，已删除。Turnstile 不等同于 TOTP 或双因素认证，当前选择前者防自动化。

### H-2 会话不可吊销

**现象**：登出仅清除浏览器 cookie，JWT 继续有效至有效期结束（默认 168 小时）；修改密码不会使既有令牌失效。

**影响**：令牌一旦泄漏（共用设备、浏览器历史、终端记录、日志），攻击者可用满 7 天，受害者改密码也无法踢出。

**修复**：`model.User` 增加 `TokenVersion`，签发时写入 claims，`CurrentAuthUser` 校验与数据库一致；改密、登出、封禁时自增。后台会话单独设置较短有效期（建议 12 小时）。

### M-1 邮箱验证码限流可被 `X-Forwarded-For` 绕过

**现象**：`handler/auth.go` 的 `requestRemoteIP` 在对端为回环地址时信任 `X-Forwarded-For`。线上 Go 服务位于 Next 代理之后，所有请求对端均为 `127.0.0.1`，Next 会透传该头；端到端是否可控还取决于入口代理是否覆盖，必须结合部署验证。

**影响**：`service/email.go` 中每 IP 每分钟 5 次的限制可能被绕过；仍有每邮箱 60 秒重发间隔、已注册邮箱与域名校验，不能声称可无间隔轰炸任意邮箱。

**修复**：入口代理先从可信 TCP/CDN 链恢复地址并覆盖头，使用私有代理密钥标识；Next 剥离非可信来源头，Go 仅信任通过密钥校验的地址。未配置时退回 TCP 对端，不信任任意 XFF/CF 头。具体部署见内部加固说明。

### M-2 审计日志客户端 IP 恒为 `127.0.0.1`

**现象**：`router.go` 的 `SetTrustedProxies(nil)` 配合反向代理，使 `middleware/observability.go` 记录的 `client_ip` 全部为 `127.0.0.1`。

**影响**：入侵溯源失效，也是 H-1 爆破长期无法被发现的原因。

**修复**：与 M-1 共用真实 IP 方案，同时将登录失败事件写入结构化日志并接入告警。

### M-3 缺失安全响应头，后台页可被 iframe 嵌入

**现象**：`/` 与 `/admin` 均无 CSP、`X-Frame-Options`、`X-Content-Type-Options`、HSTS、`Referrer-Policy`。

**影响**：管理员登录态下可被点击劫持，诱导在后台执行操作；缺少 HSTS 无法在后续连接中强制 HTTPS；普通 HSTS 也不能单独保护首次连接。

**修复**：后台及后台登录页禁止嵌入；普通页面保留自身与既有 New API 来源。禁止把 DENY 或 frame-ancestors none 应用到整个站点，以免阻断画布内嵌。HSTS 仅在生产启用，不默认覆盖所有子域。

### M-4 变更日志接口匿名暴露内部架构

**现象**：`/api/app/releases` 无需登录即可读取约 71KB 变更日志，包含上游 SDK 版本、住宅代理出口策略、号池模型映射等实现细节。

**影响**：直接降低攻击者侦察成本，暴露供应链与代理链路等敏感设计。

**修复**：拆分为「对外 release notes」与「内部 changelog」，对外版本剔除实现细节与内部术语。

### M-5 认证失败统一返回 HTTP 200

**现象**：未授权与认证失败均以 `200` 承载 `code:1`。

**影响**：WAF、CDN 规则与监控告警无法基于状态码识别爆破流量，仅按状态码聚合的告警难以识别；访问频率等其他信号仍可用于检测。

**修复**：未认证返回 401，已认证但权限不足返回 403，限流返回 429；保留 code/data/msg 结构。

### M-6 注册接口可枚举用户名

**现象**：提交合法邮箱域与 6 位验证码时，接口对已注册用户名返回「用户名已存在」，对未注册用户名返回「邮箱验证码无效或已过期」。

**影响**：无需验证码即可确认任意用户名是否注册，为撞库与口令喷洒提供目标筛选。

**修复**：先验证邮箱验证码，再检查用户名/邮箱冲突；无效验证码不能揭示用户名是否存在，已验证邮箱后的注册冲突仍可提供可操作的提示。

### 低危

| 编号 | 问题 | 修复建议 |
| --- | --- | --- |
| L-1 | 修改密码仅要求 6 位，与首建管理员 12 位策略矛盾 | 统一为至少 12 位并做弱口令字典校验 |
| L-2 | 登录对「存在/不存在用户」存在约 30ms 时序差（bcrypt 仅对存在用户执行） | 用户不存在时同样执行一次假比较 |
| L-3 | 后台无防自动化校验 | 本轮接入 Turnstile；TOTP 属于另行规划的双因素能力 |

| L-5 | 登录日志未单独记录失败事件 | 结构化记录账号、IP、结果并告警 |

## 三、原报告列出的安全控制（覆盖范围有限）

以下是原报告的检查范围，不把源码推断等同于完整黑盒验证；修复时保留已有防护并补充实际验收：

- **纵向鉴权**：`AdminAuth` 从数据库读取角色，JWT 中的 `role` 声明不参与鉴权，权限判断不直接依赖客户端角色声明；仍必须验证 JWT 签名与有效期。
- **横向鉴权**：企业域接口通过成员表校验，`X-Organization-ID` 与 `organization` 查询参数两条通道都被拦截。
- **密钥管理**：`JWT_SECRET` 强制 ≥32 位、不自动生成、无默认值；管理员密码强制 ≥12 位且拒绝默认值。
- **SSRF 防护**：https-only、禁止 URL userinfo、dial 阶段校验解析后 IP 为公网单播（排除私有段与 `100.64.0.0/10`）、禁止跳转至非 https，旨在防止 DNS rebinding，具体出网调用链仍需分别覆盖。
- **存储路径**：工作区 `storageKey` 使用严格白名单正则，并按企业隔离查询。
- **输出编码**：源码检索未见 dangerouslySetInnerHTML，尚不足以排除 URL、媒体、第三方组件等其他注入面。
- **缓存策略**：账号数据接口统一 `no-store`，且响应带 `Vary`，已检视请求未观察到泄漏，仍需覆盖不同用户与媒体缓存变体。

## 五、复测方法

以 [加固部署与验收](./security-hardening.md) 为准，覆盖正向登录、限流并发、别名切换、真实 IP 信任链、吊销、后台禁嵌与正常画布嵌入。代码完成先进入待测试；用户确认后再关闭对应项。本轮没有进行线上复测。

## 六、说明

本轮未执行 DoS 与大规模凭据爆破。证明「无速率限制」所需的证据量很小，增加请求量不会提升结论质量，也可能触发边缘防护并影响正常流量；后续测试须限定自有账号、请求预算和停止条件；DoS 亦会波及同机部署的其他服务，超出授权范围。

后续如继续深入，建议在已认证面上重点覆盖：生成接口的上游媒体回源、Agent 记忆与工具结果的跨租户隔离、批量任务归档的租户边界。这三处涉及服务端主动出网与文件落地，是当前尚未被覆盖的剩余面。
